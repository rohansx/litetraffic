Why this exists

A response is only half the story.

Load tests count responses. A real user carries state across requests, retries an action, and expects the system to leave the right result behind. LiteTraffic tests that complete chain.

What a load test seesHTTP 200 31 ms
What the customer gets2 charges for 1 payment

A fast response can still be a failed checkout.

Inside a verification run

Make a world. Run it. Check it.

01

Own the starting state

Create run-owned records over HTTP, or run setup and teardown commands such as a seed and reset script. Teardown runs even after a failure. Give each journey its own item from a fixture pool.

fixtures
02

Drive complete journeys

Carry IDs and identities from one request to the next, with an HS256 test JWT minted per actor class or one per identity. Admit journeys on a seeded clock with stock k6, pinned to one version so runs stay comparable. Declare which status codes an operation is meant to return, so an intended 403 is not counted as a failure.

k6 v2.2.0
03

Observe the final effect

Read the resulting state once the traffic stops, with one or more final observations. Match values exactly or with gte, lte, len and exists, write expected values as ${planned_journeys * 100}, and poll with until when the app settles asynchronously.

verdict
04

Check the pressure was real

A client-side overlap check reports peak in-flight requests per operation and holds back a pass when a journey's min_overlap was not reached. It shows requests were in flight together, not that the server ran them concurrently.

overlap
05

Keep the evidence

Write owner-only artifacts atomically: a digest over the manifest, script, imports and fixture files, assertion events with expected and actual values, metrics, and a standalone report. Declared secrets and minted tokens are replaced with [redacted].

artifacts

litetraffic init tenant-isolation

From two identities to a tenant-isolation check.

Describe who owns what in a small JSON config. The generator writes a complete scenario bundle for you to review and run, with no k6 code to write. The same config always produces the same files and the same digest.

own_access
Each owner can read its own resources through every read endpoint.
cross_tenant_read_blocked
The other identity gets 401, 403 or 404.
cross_tenant_write_blocked
Its writes to that resource are rejected the same way.
victim_unchanged
The owner reads the resource before and after each cross-tenant write, and both reads must match. This catches a server that answers 403 but applies the write anyway.

Local dashboard

Read the failure, not a log.

When a check fails, the run keeps the first failing samples with what the scenario expected and what the app actually did. litetraffic dashboard lists every run on your machine, filters them by scenario, verdict and seed, compares any two you tick, and charts p95 latency per scenario.

  • Binds to 127.0.0.1 only, with no host option. Requests with any other Host header are refused.
  • Read-only. It serves run artifacts and never contacts a target.
  • Follows your light or dark setting, and fits a phone screen.
  • Python standard library. Nothing else to install.

The CLI

Nine commands.

Most print a short summary for people, or one JSON object with --json for scripts and agents.

doctor
Checks k6 is exactly v2.2.0, Python is 3.11 or newer, the output directory is writable with 100 MiB free, and, with --target, that the app answers.
init
Generates a tenant-isolation scenario bundle from a small JSON config, then validates it the way inspect does.
inspect
Validates a scenario and explains it: actors, budgets, fixtures, secret variable names, observations with resolved expected values, and the schedule. Runs nothing.
approve
Records a local approval that binds the scenario's digest to a target origin. verify --require-approval then refuses to run a scenario that changed after review.
verify
Runs the scenario against a target and prints the verdict, each assertion, any limitations and the path to report.html. Repeat it across seeds with --repeat.
diff
Compares a baseline and a candidate by run directory or run ID, with an optional p95 regression gate.
dashboard
Serves your runs on 127.0.0.1 so you can filter them, read failing samples, chart a scenario over time and compare two runs.
up
Repeats bounded runs as slices until Ctrl+C or a slice limit. It records each slice and gives no overall verdict.
prune
Deletes old run directories by count or age, with a dry run to list them first.

Exit codes for verify

  • 0pass
  • 1fail
  • 2inconclusive
  • 3error
  • 130cancelled

A target that never returns an HTTP response is an error, not a pass. A missing or mismatched approval also exits 3 before anything runs. Cancelling with Ctrl+C still saves the evidence collected so far. diff uses 0, 1 and 2 the same way for its comparison. Every command exits 2 on a usage error and 3 on an error. Exit codes for every command

Works with a running HTTP app

Bring the target.
Keep the contract.

Run the same reviewed scenario against localhost, a CI preview, or an existing E2B sandbox. Target addresses and secrets stay outside the portable scenario.

  • --target Local development
  • --target CI and preview URLs
  • --e2b-sandbox-id Existing E2B sandbox

Cloud metadata and link-local addresses are refused, in any spelling, before a request is sent. URLs with embedded credentials are refused, and k6 does not follow redirects.

Developer preview

Start with a scenario you can read.

Scenarios are handwritten k6 journeys, or generated by init tenant-isolation, and you review them before running. Install k6 v2.2.0 separately, then install LiteTraffic from source.

Works today

  • Nine commands, local runs and repeats
  • Tenant-isolation scenarios from a JSON config
  • Seeded traffic profiles and budgets
  • Fixtures, test JWTs and final observations
  • Reports, approvals and run comparison

Not shipped yet

  • AI or automatic scenario authoring
  • Persistent users across runs
  • Managed sandboxes
  • A PyPI release
